# lift-telemetry: approach review (2026-11-22)

After three checked workouts (Nov 1, 14, 22; 69 checked sets) this is a step back: what
the system does, what limits it, where it wastes effort, what is wrong, and what newer
techniques would do better. Every number comes from `vbt.evaluate`, the shadow tests in
`data/sessions/*/shadow.json` or a profile run on this machine. Recommendations are ranked
by expected effect on the north star: sensor-only **readiness**, the share of logged
sets found, named and counted exactly with the log hidden.

## 1. Where it stands

| | Nov 1 | Nov 14 | Nov 22 | all |
|---|---|---|---|---|
| Log-guided detection recall | 100% | 100% | 100% | 100% (IoU 0.80) |
| Sensor-only: found | 22/22 | 17/21 | 20/24 | 88% |
| Sensor-only: named | 13 | 11 | 14 | 57% |
| Sensor-only: reps exact | 9 | 5 | 8 | 33% |
| Readiness (fully right) | 32% | 14% | 33% | 26.9% (18/67) |
| Public RecoFit: reps within ±1 | | | | 76% (published method: 93%) |

With the log, the system is in good shape: every set is placed. Without the log it
gets about one set in four fully right. Here is where the other 49 of 67 checkable sets
are lost (shadow tests, all three days, after today's changes):

| Failure | Sets | Main cases |
|---|---|---|
| Found, wrong exercise | 21 | deadlift ↔ split squat (5); pulldown ↔ bench (5); squat → pulldown (2); deadlift → leg curl (2); 3 are only a name mismatch (Triceps Pushdown vs Triceps Rope Pushdown) |
| Right exercise, reps off | 20 | 15 off by exactly one (bench 5, squat 4); 5 off by 2 or more |
| Not found | 8 | leg curl 2, pulldown 2, one each of deadlift, bench, curl, raise |

So naming and the ±1 edge rep matter about equally, and both cost far more than finding
sets. Confusions come in pairs that share a wrist pose, which says the features describe
the pose well and the movement poorly.

## 2. The approach, in one paragraph

Classical signal processing plus small-data learning. The watch's gravity vector and
user acceleration are resampled to 25 Hz. Vertical acceleration is integrated twice
through a fixed 0.2–3 Hz band-pass to get "wrist height". Reps are peaks in height, or
in one gravity axis, chosen per exercise by a hand-written profile. Set candidates are
runs of regular peaks. With a log, an ordered dynamic program assigns logged sets to
candidates. Without one, each candidate is scored against every known exercise's
prototype: a nearest centroid over 16 hand-crafted features plus a rep-shape vector.
`vbt.personal` learns per-exercise settings from checked sets, but adopts one only when it
beats the generic setting on held-out sets from at least 2 workouts.

## 3. What is right and should stay

- **Honest evaluation.** Leave-one-session-out, the shadow test, an append-only history and
  a public cross-person benchmark (RecoFit). Most hobby projects never get this far.
- **The log-guided dynamic program.** It is the right model (an ordered alignment, close
  to an HSMM), and it is now at 100% recall.
- **Adoption gated on held-out evidence.** This is what stopped Nov 1's overfit rep
  signals (held-out error 0.64 vs 0.45). Pulldown is the first learned setting that passed
  (gy/top, held-out error 1.00 → 0.00).
- **A small, deterministic, dependency-light codebase**: 4.3k lines, numpy/scipy/sklearn.

## 4. What is wrong (correctness)

1. **Fixed today: learned evidence mixed code versions.** `evidence.json` was rebuilt
   only when `sets.json`'s file *mtime* changed. After an algorithm change, `vbt.evaluate`
   scored new code against prototypes built by old code. A fresh clone rebuilt everything,
   because mtimes differ, while the working copy did not. The same commit scored 26.9% and
   23.9% readiness depending on that. Now keyed on `sets.json` content plus a hash of the
   modules that build evidence, and refreshed before `run` and `evaluate`
   (`personal.refresh_evidence`). Scoreboard lines recorded right after an algorithm
   change, before a full `run --all`, may carry this bias.
2. **Log order is assumed to be execution order.** Today's two supersets were not
   declared, so the automatic order was wrong from the 15th set on. Hevy lists sets
   exercise by exercise. Supersets should be detected, not declared (§6.4).
3. **Exercise identity depends on exact names.** "Triceps Pushdown" vs "Triceps Rope
   Pushdown" and "Lat Pulldown (Cable)" vs "Pulldown (Wide Parallel Grip)" are separate
   exercises to the learner. That costs 3 readiness sets today and splits the evidence.
   Fix: ask once per new name (`data/aliases.json`) as part of every workout.
4. **Velocity on slow reps.** The fixed 0.2 Hz high-pass cannot represent a rep slower
   than ~5 s. Heavy deadlifts (5–6 s per rep) come out as split "ghost" cycles and
   unreliable velocities (Nov 22: 0.12 m/s for a 120 kg set). The ghost filter fixes the
   count, not the kinematics (§6.2).
5. **Many thresholds were tuned on a single day.** `infer.is_set`, `GHOST_ROM`,
   the ~20 weights and limits in `align_sets` and others carry comments like "tuned on Nov 1". With
   67 checked sets, one set is 1.5 points of readiness, so small gains are noise. Needed:
   bootstrap confidence intervals on the scoreboard, and tuning only on folds that
   exclude the test day.

## 5. Efficiency

**Compute.** A profile of one `pipeline run` (Nov 22, 82 s under the profiler):
- 22 s went to re-*designing* the same Butterworth filters, 58,792 times. **Fixed today**
  with a cache; output is bit-identical. `vbt.evaluate` went from 6.1 to 4.3 min.
- 12 s goes to `resample` and ~20 s to `position`, called ~10,000 times on overlapping
  windows. Filter the whole session once at 25 Hz, then slice; integrate per window only
  the slice. Expected: another ~2× speed-up, so `vbt.evaluate` would take about 2 min.
- 12 s goes to random-forest fits in the report's classifier block (25 fits). Use fewer
  trees, or cache fits per session set.

**Human time, the real bottleneck.** Reviewing a workout took most of today's session.
The decisive views (whole-session orientation lanes, floor-contact spikes, the
arm-overhead test for pulldown) were ad-hoc scripts, not part of `pipeline review`. Three
changes would cut review time by most:
1. `pipeline review` should also render a **whole-session overview**: gravity lanes,
   current windows, the sensor-only guesses, and where the two disagree. Disagreements are
   where to look; everything else is usually right. (Done today: `review_overview.png`.)
2. **Label at the source.** Sensor Logger writes a `Tags.csv` (empty today). If a tag or
   annotation can be tapped at the end of each set (phone or watch), set boundaries become
   free and exact, and review becomes a glance. Worth checking what the app allows during
   a workout.
3. **Ask the user three things with every log:** supersets, new exercise names
   (aliases), and anything done but not logged.

**Storage.** The 25 Hz copy drops what the faster channels carry: impact spikes (the
deadlift floor contact is a 1–2 sample event at 25 Hz), the uncalibrated accelerometer
file and heart rate. Store 50 Hz (about 2× the size, ~8 MB per workout) plus heart rate.

## 6. Better methods, ranked

### 6.1 Naming: add the features the confusions point to (small, now)
Deadlift vs split squat (5 sets) share a hanging-arm pose. The deadlift has a sharp
floor-contact spike per rep that dumbbell work never has. Add **impact rate**: spikes in
vertical jerk per rep. Pulldown vs bench (5 sets) share gravity on +x; the body is upright
in one and lying in the other. Add **pre-set posture**: the orientation in the 10 s before
the set, and the travel direction relative to gravity. Both are cheap and directly target
about 10 of the 21 misnamed sets.

### 6.2 Reps: one period estimate per set, not peaks on a fixed band (medium)
The ±1 edge rep is the single biggest rep error (15 sets). The fixed 0.2–3 Hz band is
also why slow reps split. Better, in order of effort:
- **Set-adaptive band.** Estimate the rep period from the set's autocorrelation first
  (this is how RecoFit reached 93% within ±1), then band-pass around *that* frequency.
  This removes ghosts at the source instead of filtering them afterwards.
- **Channel-agnostic rep signal.** Use the first principal component of the 6-axis
  window (accelerometer + gyro) instead of a hand-picked axis, so no per-exercise
  channel learning is needed for counting.
- **Rest-anchored (ZUPT) integration for velocity.** Integrate each rep between two
  detected still points, as dedicated VBT IMUs do. Prototyped today: promising but
  sensitive to the stillness threshold (3–6 of 13 deadlift sets exact across settings),
  so not adopted. It needs the 50 Hz data and a learned threshold.
- **Personal rep templates (DTW).** Match a stored rep template of this exercise; the edge
  rep is the one whose shape matches neither "setup" nor "rep". This is the few-shot
  idea in recent IMU rep-counting work (e.g. arXiv 2410.00407).

### 6.3 Set-vs-noise: learn it now (small)
`infer.is_set` is hand-tuned on Nov 1 and lets 9 false sets through across 3 days. Three
checked workouts give labelled negatives for free (every candidate outside a checked
window). Train a logistic regression or small gradient-boosted model on the candidate
features, scored leave-one-session-out. This was planned "at ~5 workouts"; there is
enough now to start.

### 6.4 Supersets and order: let the aligner choose (small)
Run the dynamic program over each plausible order: as logged, and with adjacent exercise
pairs interleaved. Keep the best-scoring one. That is 2^(pairs) cheap runs, and it would
have handled today without a hint.

### 6.5 Learned representations: pretrain, then few-shot (larger, next stage)
The state of the art for wrist IMUs is self-supervised pretraining on large unlabelled
data, then a small head fitted on a few labels:
- **Oxford ssl-wearables (harnet5/10/30):** pretrained on 700k person-days of UK Biobank
  wrist data; 3-axis accelerometer at 30 Hz in 5/10/30 s windows; loads via
  `torch.hub.load('OxWearables/ssl-wearables', 'harnet10', pretrained=True)`; fine-tuning
  improved F1 on every public HAR benchmark it reports. **Licence: academic research only**,
  so check that before relying on it. A 10 s window spans 2–4 reps, so it suits naming,
  not counting.
- **Google LSM** (40M hours, 165k people) shows wearable foundation models are very
  label-efficient, but its weights are not public.
- Language-aligned IMU models (IMU2CLIP, HALO) target open-vocabulary recognition, such as
  naming an exercise never seen before. Interesting, but a new exercise is rare for one
  person.

The practical path: (a) extract harnet10 embeddings per set (or train a small encoder of
your own on your unlabelled hours plus RecoFit), (b) feed them to the existing nearest-
prototype step next to the hand features, (c) keep it only if leave-one-session-out
naming improves. Expected gain is largest on the 21 misnamed sets. A fully learned
per-sample model (a temporal CNN labelling set / rep phase) is the end state. It
needs a few hundred checked sets: about 10 more workouts at ~23 sets each, or fewer if
pretrained on RecoFit and MM-Fit (Strömbäck et al. 2020, includes smartwatch data).

### 6.6 Velocity: what the wrist can and cannot do
Published validation (Achermann et al. 2023, Apple Watch 7, back squat): wrist-worn
mean velocity r = 0.95–0.97, SEE 0.064 m/s, about as good as a bar-mounted commercial
IMU. So squat and bench velocity from the wrist is sound once reps are isolated. The weak
spots are slow pulls (§4.4) and any lift where the wrist rotates a lot (curls, raises).
Velocity should only be reported for barbell lifts.

## 7. Proposed order of work

| # | Change | Effort | Targets |
|---|---|---|---|
| 1 | Ask for aliases / supersets / unlogged sets with each workout | none | 3+ sets, review time |
| 2 | Impact-rate and pre-set-posture features | small | ~10 misnamed sets |
| 3 | Learned set-vs-noise filter (leave-one-session-out) | small | 9 false sets |
| 4 | Superset / order search in the aligner | small | review time, robustness |
| 5 | Whole-session overview in `pipeline review` | done today | review time |
| 6 | Bootstrap CIs on the scoreboard; tune only out-of-fold | small | trust in every result |
| 7 | Session-wide filtering (2× faster evaluate) | small | iteration speed |
| 8 | Set-adaptive band / autocorrelation period for counting | medium | 15 off-by-one sets, ghosts |
| 9 | 50 Hz storage + heart rate | small | enables 8, 10 |
| 10 | Pretrained embeddings for naming (harnet or own encoder) | medium | misnamed sets |
| 11 | Rest-anchored velocity | medium | heavy-lift velocity |
| 12 | Learned per-sample model | large | end state; needs ~300 checked sets |
